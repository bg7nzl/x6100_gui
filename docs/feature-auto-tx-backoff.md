# 自动发起的重试退避

源码：`src/ft8/qso.cpp` 里的 `auto_tx_text_allowed`、`blacklist_*`；常量 `AUTO_TX_TEXT_SOFT_MAX`、`AUTO_TX_TEXT_HARD_MAX`。
测试：`tests/test_ft8_qso.cpp`。

## 背景

自动模式会主动发起通联——回别人的 CQ，或者在别人收工（RR73 / 73）后 tail-end 抢一把。这两种都是 `compute_one` 里 order ≤ 2 的候选，共同点是对方还没点名叫我。问题在于：对方要是一直不搭理，同一条 Tx2 会一遍遍地发，既白费功夫，也在给频段添堵。

反过来，一旦对方叫了我（order ≥ 3，report / R±nn / RR73 / 73），那就是一场正在进行的 QSO，回复必须干脆，不该因为“之前试过几次”被压下去。所以这套限制只管发起，不碰进行中的 QSO。

代码里这块沿用了 blacklist 这个名字，但它其实不是“拉黑名单”，而是给每条发起报文一个有限的重试预算。

## 为什么按发送次数算，而不是按时间

能限制的只有自己发了几次，管不着对方多久冒一次头。而且同一个目标，所处环境天差地别：有的台连着 CQ，半分钟就给一次机会；pileup 里的 DX 可能一整场 QSO 结束才露一次脸。拿墙钟去卡，很难同时照顾这两头。

改成“同一条 TX 文本已经实际发了几次”就自然多了——机会密的地方次数涨得快、早早收手；机会稀的地方次数涨得慢，同样的预算能摊到很长的墙钟时间上。不用为 CQ 和 tail-end 各写一套时间窗。

键用的是完整 TX 文本（大小写不敏感），不是呼号。限制的就是“这条报文重发了多少遍”。

## 三段式

```text
count < 3         直接放行
3 ≤ count < 10    概率放行，p = p0 · 0.9^(count-3)
count ≥ 10        彻底停发
```

前三次无条件发。头几次没回应太正常了——衰落、QRM、对方在解别的台、两边同时发撞了车——犯不着一次没成就开始退。

从第 4 次起按概率放行，概率随已发次数往下掉。CQ 起点高、tail-end 起点低：

| count | CQ (p0=0.70) | tail-end (p0=0.35) |
|-------|------|------|
| 3 | 70% | 35% |
| 4 | 63% | 32% |
| 5 | 57% | 28% |
| 6 | 51% | 26% |
| 7 | 46% | 23% |
| 8 | 41% | 21% |
| 9 | 37% | 19% |
| ≥10 | 停 | 停 |

到 10 次硬停。这条线不管日常退避——日常靠概率曲线——它只是根保险丝，防着某个目标长期赖在频段里、又老通不成，把选台器一直勾着。正常情况下大多数报文走不到 10：要么 QSO 成了被 remove_worked 剔掉，要么对方走了、不 CQ 了，要么拨旋钮 / 点击把决策状态清了。

## CQ 高、tail-end 低，为什么不矛盾

对方在公开 CQ，说明此刻它想通；没回可能只是没解到我、传播不够、或者被更强的台抢了，刚进退避时再试一把仍然值。tail-end 不一样，没有证据表明对方在持续找人，尤其 pileup 里一堆台在抢，每个 RR73 都跟着发就是明摆着添乱。所以 CQ 起点定 0.70、tail-end 定 0.35。

关键要看明白一点：概率低不等于更早放弃。count 只在真放行、真发了才 +1；概率没放行的那一隙，count 不动。所以低概率的效果是把有限的几次发送在墙钟上拉得更开，而不是更快撞到 hard。tail-end 机会本就稀（大约一场 QSO 一次，一两分钟级别），再叠上低概率，剩下那几次能铺到几十分钟——这正是 pileup 想要的：不刷屏，但长时间里始终留着偶尔再试一下的机会。CQ 机会密、概率又高，于是一个老不理人的 CQ 台会更快把预算烧完。

## 一路是怎么改过来的

现在这套是改了两轮才到的，中间的取舍值得记一下。

最早很简单粗暴：order ≤ 2 的同一条发起报文发满 3 次就直接封死，非黑即白。日常够用，可一进 pileup 就露馅——稀有台还没通上，3 次就到顶，之后再也不发，等于自己把机会关死了。3 这个数，日常嫌多、抢稀有台又嫌少，一个定值伺候不了两头。

第一轮改，是把这个 3 从“上限”降级成“软坎”：前 3 次照发，之后不再一刀切，改成按概率放行——CQ 50%、tail-end 25%，另外补一道 10 次的硬上限兜底。这下前几次照常、后面还能偶尔再试、真赖着不走也有 10 次封顶，比一刀切舒服多了。

第二轮改，是嫌固定概率有个别扭处：count 刚到 3（才试三次）和 count 到 9（已经发了一堆）用的是同一个概率，明明该越试越谨慎，它却一视同仁。于是把固定概率换成随 count 往下掉的曲线 `p0 · 0.9^(count-3)`，CQ 从 0.70 起、tail-end 从 0.35 起。参数是特意挑的：按 3 + 7/p 估，旧的 50% / 25% 大约对应 17 次和 31 次机会到 hard，新曲线积出来还是约 17 和约 31——总预算没动，只是把重试重新铺了一下，刚失败时比原来更肯试、反复没成之后比原来更收敛。所以这轮是“等预算换形状”，不是让它更激进或更保守。soft 3、hard 10 从第一轮起就没再动过。

## 和其它机制的关系

这道概率门在候选进选台器之前，只回答“这条发起报文这一隙准不准参赛”，不掺和排名。没过门的候选直接不进池，于是选台器可以转头去看别的目标——不是让整机空守着一个台。进了池，后面 order 最大、last_call 粘滞、SNR / 距离 / 随机 / 新网格那套照旧。

它也不是防重复的第一道闸。前面还有 remove_worked：通联过的六元组，order ≤ 2 的再次发起会被直接剔掉。所以正常通成的 QSO 不会在这里慢慢攒到 hard，这道门主要面对的是“还没通成、却老冒出同一条发起报文”的目标。

选台器选中之后还有最后一道人工门：对每个呼号，本会话第一条发起 Tx2 要操作员按键放行，确认前不烧这里的计数（见 [feature-auto-tx2-confirm.md](feature-auto-tx2-confirm.md)）。

## 实现取舍

- 概率直接用 `p0 * pow(0.9, step)` 现算，没做查表。就 count 3..9 七档，查表当然也行，但 x6100 是性能够用的 ARM，一次 `pow` 无所谓，公式摆在那儿反而一眼看得懂在干嘛。
- 计数在选中、准备发的时候 +1，不等射频确认。它是“决策层花了几次机会”的预算，不是“电波成功出去几次”的计数器。偶尔过窗没发成，也算选台器为这个目标花掉了一次，不回滚。想按射频确认计数，就得引入异步的发射完成 / 回滚状态，对这个刻意做薄的引擎不划算。
- 没有 cooldown 计时器。候选出现的疏密本身就是天然的时间尺度，再叠一层定时器是过度控制。
- 决策状态一清（`ftx_qso_clear_decision_state`，拨 CQ / Auto / Auto Mode、手动点击都会触发），整张表跟着清零。

## 改这块时注意

- 先动 `tests/test_ft8_qso.cpp`，`run_tests.sh` 跑一遍。现有用例覆盖了“软门放行时两种结果都出现”“CQ 发满 10 次后恒 RX”“清决策状态后重新放行”。
- 想调激进程度，优先动 `p0` 或衰减系数，别急着拆成 per-kind 的 soft / hard——两档共用 3 / 10、靠机会密度和 p0 拉开差异，是这套设计特意保持简单的地方。
